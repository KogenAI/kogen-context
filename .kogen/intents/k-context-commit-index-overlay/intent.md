# Add a shared per-commit search index with overlay

Slug: k-context-commit-index-overlay
Model: .kogen/intents/k-context-commit-index-overlay/model.qnt invariants=ServedFilesHaveTheCommitContent,TrustedEntriesAreOld seed=7 samples=2000 steps=20
Acceptance:
- .kogen/intents/k-context-commit-index-overlay/acceptance.feature
- features/steps/k-context-commit-index-overlay__steps.js
- features/steps/k-context-commit-index-overlay__tree.js

Every search of kogen-context (`kogen-context request` with `"operation": "search"` in both orders, and the unversioned `kogen-context search ROOT LITERAL`) on a root inside a Git checkout now uses an index of the checkout's HEAD commit. The index lives in the per-user cache directory, outside the selected root, and every run of the same user on the host shares it. The working tree's uncommitted state is overlaid on it on every search: edited, added (untracked or ignored) and deleted files are visible in the next search, and nothing is rebuilt for them. The index changes speed only. Every packet, every CLI output, every exit status and the empty stderr are byte for byte what the same search prints today without an index, and the checkout, including its `.git`, is never written. Repeat searches on one commit must take at most the time of a path-sorted ripgrep scan of the same tree. This is measured on a generated fixture, the repository fixtures and the two pinned Crane revisions.

This replaces the stateless search: today every search rescans the whole checkout and nothing is stored between runs. It also replaces the earlier pin that a search runs no other program and opens nothing for writing. A cold search on a Git checkout now runs `git` read-only and writes in the cache directory. Outside Git checkouts, and when no usable cache directory exists, a search behaves exactly as today. `read`, `version`, the request and packet schemas, the error codes and messages, the golden packets, the contract examples and `scripts/crane-replay.sh` do not change. No request member, packet member, command-line flag or environment variable of kogen-context is added. (`KOGEN_CONTEXT_BENCH_REPORT` below belongs to the benchmark test only.) Use only the Rust standard library and add no crates (`--locked --offline`). `rust-toolchain.toml` stays unchanged.

The change also adds `tests/index.rs` (integration tests), `tests/index_bench.rs` (an ignored benchmark test against ripgrep) and `scripts/crane-bench.sh` (a benchmark replay on the pinned Crane revisions), and updates `contract/README.md` and `README.md`.

**The cache directory (the index location)**

- Base: `$XDG_CACHE_HOME` when that variable is set to an absolute path (on every platform). Otherwise `$HOME/Library/Caches` on macOS and `$HOME/.cache` on every other platform, when `HOME` is set to an absolute path. An empty or relative `XDG_CACHE_HOME` is ignored. With no absolute `XDG_CACHE_HOME` and no absolute `HOME`, there is no cache directory.
- The cache directory is `<base>/kogen-context`. The index files are `<base>/kogen-context/index-v1/commits/<commit>` (the commit index) and `<base>/kogen-context/index-v1/trees/<commit>-<root key>` (the tree snapshot). `<commit>` is the full lowercase hexadecimal commit id. `<root key>` is the FNV-1a 64-bit hash (offset basis `0xcbf29ce484222325`, prime `0x100000001b3`) of the bytes of the canonical root path, written as 16 lowercase hexadecimal digits. Nothing else is ever left in the cache directory.
- Outside the root: resolve the longest existing ancestor of `<base>/kogen-context` with symlinks resolved, and append the missing components. If the result is the canonical root or inside it, the search uses no index and writes nothing.
- Missing directories on the way (the base itself, `kogen-context`, `index-v1`, `commits`, `trees`) are created with mode `0700`. Index files are created with mode `0600`.

**When a search uses the index**

The existing checks come first unchanged (`root_not_directory`, and for requests the parse, version and schema checks). Then a search uses the index only when all of these hold. Otherwise it is today's full scan and creates or writes nothing anywhere.
1. There is a cache directory outside the root (above).
2. The root is in a Git checkout. Starting at the canonical root and going up to `/`, the first directory with a `.git` entry is the checkout's top. If that entry is a directory, it is the Git directory. If it is a regular file whose content is `gitdir: <path>`, `<path>` is the Git directory, relative to the top when not absolute. Linked worktrees and submodules work this way. `GIT_DIR` and other `GIT_*` variables are ignored for this discovery.
3. HEAD resolves to a commit id. kogen-context reads `<gitdir>/HEAD` itself. If it holds a 40- or 64-digit lowercase hex id, that is the commit. If it holds `ref: <name>`, the ref is read from `<gitdir>/<name>`, then `<commondir>/<name>`, then the `<id> <name>` line of `<commondir>/packed-refs`, following at most 5 nested `ref:` contents. `<commondir>` is the path in `<gitdir>/commondir`, relative to the Git directory, or else the Git directory itself. If that yields no id (for example reftable refs), it runs `git --git-dir=<gitdir> rev-parse --verify --quiet HEAD`. No result (for example an unborn branch) means no index.
4. The commit index and the tree snapshot can be loaded or built (below). If `git` cannot run or fails while building, the search falls back to the full scan. A file that cannot be written (read-only or full cache) is not an error: the search still answers, from the freshly built index in memory or by the full scan.

Every `git` run uses `--git-dir=<gitdir>`, runs with the checkout's top as working directory, and has every `GIT_*` variable removed from its environment, then `GIT_NO_LAZY_FETCH=1` and `GIT_TERMINAL_PROMPT=0` set. Its stdin is null except for `cat-file`, and its stderr is discarded. kogen-context runs only `git ls-tree`, `git cat-file` and `git rev-parse`, which write nothing to the repository. kogen-context prints nothing about the index, and stderr stays empty on every success.

**The commit index `index-v1/commits/<commit>`**

Built when missing or invalid, from `git --git-dir=<gitdir> ls-tree -r -z --full-tree <commit>` and `git --git-dir=<gitdir> cat-file --batch`. Feed the blob ids from a separate thread so the pipes cannot deadlock. It covers every regular-file blob of the whole commit (mode `100644` or `100755`), whatever the root. Symlinks (`120000`), submodules (`160000`), paths that are not UTF-8 and blobs that `cat-file` reports `missing` are left out. Per entry it holds the path relative to the top, the blob id, whether the blob's bytes are valid UTF-8, and for UTF-8 blobs the set of distinct byte trigrams (every 3 consecutive bytes). The trigrams are stored as per-trigram ascending lists of entry numbers behind a sorted trigram directory. A search reads the header, the entry table and the directory, then only the posting lists of the literal's trigrams, never the posting data of the other trigrams. The file is immutable once published. Different checkouts, roots and processes of the user share it.

**The tree snapshot `index-v1/trees/<commit>-<root key>`**

Built when missing or invalid, and rebuilt by the racy rule below. Let `start` be the wall-clock time when the build begins. The build walks the root exactly like today's search walk, keeping the `lstat` of each file. For each file whose path (prefixed by the root's path below the top) is an entry of the commit index, it reads the working-tree bytes and compares them with the blob's bytes from `git cat-file --batch`. When the bytes are equal and both the file's mtime and ctime are more than 2 seconds before `start`, the file is trusted. The snapshot records its root-relative path, its commit-index entry and its stat key: device, inode, size, mtime and ctime in seconds and nanoseconds. When the bytes are equal but the file is too recent, the file is not recorded and the snapshot is marked racy. The header records the commit, the canonical root path, `start` and the racy mark.

Racy rule: a search that finds a valid racy snapshot more than 2 seconds after its `start` builds the snapshot again and replaces it before searching. A snapshot that is not racy is never rewritten. Edits never rewrite it. The model `model.qnt` checks that a file served from the index always has the commit's content. It explores creates, writes, mtime-restoring tools, removals, renames, inode reuse and coarse timestamps. An inclusive rule (trusting a file whose time equals the snapshot's start tick) violates it.

**A search with the index**

The search walks the root exactly as now: regular files only, symlinks not followed, every directory named `.git` skipped, non-UTF-8 names skipped, bytewise path order. It takes `lstat` from the directory entry. For each file:
- Trusted means it has a snapshot entry whose stat key equals its current `lstat`. A trusted file whose blob is not UTF-8 has no match and is not read. With a literal of at least 3 bytes, a trusted UTF-8 file whose blob lacks any trigram of the literal has no match and is not read. Every other trusted file is read from the working tree and searched.
- Every other file is read from the working tree and searched exactly as today: edited files, untracked and ignored files, files whose stat changed, racy files, and files outside the commit (for example the `.git` file of a worktree).
- Index and snapshot entries that the walk does not find (deleted files) contribute nothing.

Matching, columns, text clipping, path order with its stop after `max_matches` + 1 matching lines, ranked tiers and `truncated` all stay the existing code applied to the files it reads. So the output is identical to the full scan. A literal shorter than 3 bytes reads every trusted UTF-8 file (correct, with no speed claim). A warm search runs no other program, writes nothing, and reads only the HEAD and ref files, the index files as stated, the `lstat` of every file under the root, and the files it must read. A cold search's output is also identical.

**Files and concurrent runs**

Each index file is written to a temporary file in its final directory, named `.<final name>.<pid>.<counter>.tmp`. The writer syncs it (`sync_all`) and then renames it over the final name. On any failure the temporary file is removed. A published file is never modified in place. A reader accepts a file only if its header has the magic, format version 1, the expected kind and key (commit, plus canonical root path for snapshots), and its length matches the length the header records. Any other file is treated as absent and replaced by a fresh build. Concurrent cold searches may each build and publish the same file. Every reader sees a complete file or none. Every packet is correct, and when all runs end only the final files remain. No locks are used. Users may delete the cache directory at any time. The next search rebuilds what it needs.

**Benchmark test `tests/index_bench.rs`**

One test, marked `#[ignore = "benchmark: cargo test --release --locked --offline --test index_bench -- --ignored --nocapture"]`, so the configured `cargo test` does not run it. It needs `git` and `rg`. It fails with a message naming `rg` when ripgrep cannot run. When built without `--release` (`cfg!(debug_assertions)`), it fails with a message asking for `--release`. It uses `env!("CARGO_BIN_EXE_kogen-context")`.
- In a fresh temporary directory it generates the acceptance's fixture: 4000 files `pkgNN/fileNNNN.zig` (`NN` = file number / 100 with 2 digits, `NNNN` = file number with 4 digits), each of 200 lines `const value_<f>_<l> = compute(<f>, <l>); // filler line of the benchmark fixture`. Line 100 of every 500th file (0, 500, ..., 3500) is `pub const marker_<f> = "needleIndexBench";` instead. It commits them with Git, with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` and a fixed author and committer. It sets every file's mtime to 2020-01-01T00:00:00Z and waits 3 seconds.
- It runs kogen-context with `XDG_CACHE_HOME` set to a directory inside the temporary directory, and computes reference outputs on a plain copy without `.git`. It measures: cold (1 request in path order), warm (5 requests and 5 ripgrep runs per order, interleaved), then appends the line `edited needleIndexBench` to `pkg12/file1234.zig` and adds `added-by-benchmark.txt` with the line `added needleIndexBench`, and measures after-edit the same way. ripgrep runs as `rg --sort path --fixed-strings --line-number --column --no-heading --no-ignore --hidden --glob '!.git' --no-messages -e needleIndexBench .` from the fixture root.
- Every kogen-context packet must equal the plain copy's packet for the same state and order. It prints exactly 5 measurement lines, in this order: `cold` `path`, `warm` `path`, `warm` `ranked`, `after-edit` `path`, `after-edit` `ranked`. Each line is `<phase>\t<order>\t<kogen-context ms>\t<ripgrep ms>`, with both times printed with exactly one decimal (`{:.1}`). kogen-context's time is the single run for `cold` and the median of 5 runs otherwise. ripgrep's time is the median of its 5 runs in that phase and order. For `cold`, it is the median of the warm `path` ripgrep runs.
- When the environment variable `KOGEN_CONTEXT_BENCH_REPORT` names a file, the test also writes those same 5 lines there, each ending in a newline. It writes them before its timing assertion, so the file exists even when that assertion fails.
- It then asserts that every warm and after-edit time of kogen-context is at most ripgrep's. The failure message shows the whole table. It removes its temporary directory.
- It is the repository's only ignored test, so `cargo test --release --locked --offline -- --ignored --nocapture` runs exactly it.

**Crane benchmark replay `scripts/crane-bench.sh`**

A POSIX `sh` script, mode 755, runnable as `sh scripts/crane-bench.sh BINARY`, in the style of `scripts/crane-replay.sh`. It needs `git`, `rg`, `tar`, `python3` and network access to GitHub.
- Arguments: exactly one, a `kogen-context` binary. Any other count prints exactly `usage: scripts/crane-bench.sh BINARY` and a newline on stderr, nothing on stdout, and exits 2 before doing anything else. Every other failure prints one line starting with `crane-bench.sh: ` on stderr and exits 1.
- It makes one directory with `mktemp -d` (under `TMPDIR` when set) and removes it on exit, on success, failure, `HUP`, `INT` and `TERM`. It sets `XDG_CACHE_HOME=<tmp>/cache` for every kogen-context run, so the user's cache is never used and the first search of each revision is cold. It writes nothing else anywhere.
- Revisions, in order, as in `scripts/crane-replay.sh`: label `adc2ea58b65`, commit `adc2ea58b65af01f112e0fa4cfd91520cb78a766`, and label `b41782ab61d`, commit `b41782ab61da93c80ca6c0fa8c83ff3ceb5ac99c`, of `https://github.com/zig-whatwg/crane.git`. It fetches both by id with `git fetch --depth 1` into a repository it initialises at `<tmp>/repo`, and checks that each commit exists under that exact id. For each revision it creates a linked worktree with `git -C <tmp>/repo worktree add --detach <tmp>/<label> <id>` (the indexed checkout) and a plain export `<tmp>/<label>-plain` with `git archive` and `tar` (the reference without Git). Then it waits 3 seconds so that every checked-out file is more than 2 seconds old.
- Hints, in order: `spinEventLoopUntil`, `evaluateReplScript`, `journal.shard`, `wptreport.jsonl`, `cleanup`, `gen_snapshot`, `constructorCallback`. Request: `{"version":1,"root":"<absolute worktree>","operation":"search","literal":"<hint>","order":"<order>"}` to `BINARY request`. ripgrep: `rg --sort path --fixed-strings --line-number --column --no-heading --no-ignore --hidden --glob '!.git' --no-messages -e <hint> .` from the worktree.
- Per revision, in order:
  - cold: 1 timed request for `spinEventLoopUntil` in path order, with the median of 3 ripgrep runs for that hint.
  - warm: for each hint, then each order `path` and `ranked`, the medians of 3 timed requests and 3 timed ripgrep runs.
  - The edit, applied to both the worktree and the plain export: append the line `// crane-bench: spinEventLoopUntil evaluateReplScript journal.shard wptreport.jsonl cleanup gen_snapshot constructorCallback` to `build.zig`, write that line as the only line of the new file `crane-bench-added.zig`, and delete `CHANGELOG.md`.
  - after-edit: the same measurements as warm.
- Every timed request must exit 0 and print exactly the stdout of the same request on the plain export in the same state. Otherwise the script fails with `crane-bench.sh: packet differs for <hint> (<order>, <phase>) on <label>`. ripgrep must exit 0 or 1.
- Times are wall-clock milliseconds of the whole process, measured with `python3` `time.perf_counter()`. Output: one record per measurement, `<label>\t<phase>\t<order>\t<hint>\t<kogen-context ms>\t<ripgrep ms>`, with both times printed with exactly one decimal (`%.1f`). Phases are `cold`, `warm` and `after-edit`. That makes 29 records per revision, 58 in all, in the order above, and nothing else on stdout. The script exits 0 after the last record and judges no time. The acceptance scenario does.

**Contract and README**

`contract/README.md` replaces "Each run is stateless: one request in, one packet out, nothing stored between runs." with the index rules. The packet still depends only on the request and the files under the root, and packets are byte-identical with and without the index. A search may keep an index in the per-user cache directory, `$XDG_CACHE_HOME/kogen-context` (absolute `XDG_CACHE_HOME`), else `~/Library/Caches/kogen-context` on macOS and `~/.cache/kogen-context` elsewhere, in `index-v1/commits/<commit>` and `index-v1/trees/<commit>-<root key>`. The index is never inside the root, is shared and safe for concurrent runs, and may be deleted at any time. Packets carry no index or freshness field. The README states that this is the expand step of expand-then-contract: no request or packet member is added or removed, version 1 is unchanged, and nothing is contracted. The schemas and `contract/examples/` do not change.

`README.md` updates these parts:
- "Current state" mentions the index.
- A "Search index" section gives the cache location (including `$XDG_CACHE_HOME/kogen-context`) and the overlay of edits.
- A benchmark section gives `cargo test --release --locked --offline --test index_bench -- --ignored --nocapture` (needs `git` and `rg`) and `sh scripts/crane-bench.sh target/release/kogen-context` after `cargo build --release --locked --offline` (needs network, `git`, `rg`, `tar` and `python3`).
- The source map names `tests/index.rs`, `tests/index_bench.rs` and `scripts/crane-bench.sh`.
- The sentence "the replay script above is the one script that uses the network" becomes a statement that `scripts/crane-replay.sh` and `scripts/crane-bench.sh` are the only scripts that use the network.

**What the tests do not prove.** The scenarios observe outputs, cache files and checkout state on small fixtures, a generated 4000-file fixture, the repository fixtures and Crane. They do not prove byte-identity for every tree. The timestamp race is covered by the Quint model and unit tests, not by a reproduced race. The timing scenarios compare medians on the host that runs them, with the `rg` on its `PATH`.

## Decisions
- The index is a speed change only: packets for the same tree state are byte-identical with and without it, so no request or packet member and no freshness field is added (source: request)
- The index is keyed by commit and shared by all agents of the user on a host through a per-user cache directory with a stated location, outside the selected root (source: request)
- The working tree's uncommitted edits are overlaid: edited, added and deleted files are visible in the next search without rebuilding the index (source: request)
- The checkout stays read-only and concurrent agents are safe with the shared index (source: request)
- Benchmarks live in the repository: a benchmark test comparing cold, warm and after-edit times against ripgrep on a fixture, and a replay script for the pinned Crane revisions (source: request)

## Feasibility
- Crane (pinned `adc2ea58b65` as a Git worktree on this Linux host, 4 cores): 9,326 files, of which 9,308 are UTF-8 (108 MB). Path-sorted ripgrep 14.1.0 with the options above took about 110 ms per search. A full `find` walk with `lstat` of every file took about 30 ms, and the current debug binary about 1.1 s. A trigram index of it has 176,510 distinct trigrams and 12.6 million (file, trigram) pairs, so posting lists must be read selectively. (scratch probes, outside the repository)
- Tiny fixtures (`tests/corpus/go`, `tests/ranking/repl`, `contract/examples/checkout`), medians of 11 runs from Node `spawnSync`: spawning `/bin/true` costs 2.1 ms, ripgrep 3.8 to 4.4 ms, the current debug kogen-context 2.6 to 3.5 ms, and `git rev-parse HEAD` 2.8 to 3.3 ms. A warm search therefore must not spawn `git`, which is why HEAD is resolved in-process. ripgrep and kogen-context count the same matching lines on all six repository fixtures for the acceptance literals.
- `git worktree add -q --detach` of both pinned Crane commits works with git 2.43. The worktree's `.git` is a `gitdir:` file, and its HEAD holds the detached id.
- Quint: `model.qnt` typechecks and runs with `--invariant='ServedFilesHaveTheCommitContent and TrustedEntriesAreOld' --seed=7 --max-samples=2000 --max-steps=20` without a violation (about 5 s). With the trust rule made inclusive (times at or before the start tick), the run finds a violation of `ServedFilesHaveTheCommitContent` within 105 ms.
- The step definitions bind every step of the feature (Cucumber dry run in a scratch copy: 22 scenarios, 240 steps, none undefined).
- On HEAD, `cargo test --release --locked --offline -- --ignored` exits 0 after about 4.5 s, running 0 tests because the repository has no ignored test. Its runner output is accepted. The benchmark-test scenario then fails at "the benchmark report lists exactly these measurements", because no report is written. That is the missing benchmark, not a broken fixture.
- Baseline run of selected scenarios in a scratch copy of HEAD, with the release build. The first scenario fails at the cache listing, because no index file exists yet. The racy scenario fails when it notes the cache, because the cache directory does not exist. The six no-index examples pass (preserved behaviour).
